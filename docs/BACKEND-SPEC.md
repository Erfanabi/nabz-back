# نبض — سند پروژه برای تیم بک‌اند

> این سند **توصیف کامل محصول، مدل داده و قواعد کسب‌وکار** است.
> فهرست دقیق endpointها در فایل جداگانهٔ [`API-SPEC.md`](API-SPEC.md) آمده.
>
> مخاطب: تیم بک‌اند. هدف: پیاده‌سازی سروری که اپ موجود (React Native / Expo)
> بدون تغییر در صفحه‌ها به آن وصل شود.

---

## ۱. نبض چیست

اپ **مدیریت مالی شخصی** فارسی/RTL برای اندروید و iOS.
کاربر هزینه، درآمد و انتقال ثبت می‌کند و اپ برایش خلاصهٔ ماه، گزارش،
بودجه، هدف پس‌انداز، هشدار و بینش می‌سازد.

* شناسه: `ir.nabz.app` · نام نمایشی: «نبض»
* فرانت: React Native 0.86 روی Expo 57، TypeScript، Zustand + AsyncStorage
* تقویم پیش‌فرض: **جلالی** · ارقام پیش‌فرض: **فارسی** · واحد پول: **تومان**
* احراز هویت: **شماره موبایل + OTP** (بدون رمز عبور، بدون ایمیل)
* مدل کسب‌وکار: سه پلن (رایگان / پلاس / پرو) با پرداخت کارت‌به‌کارت و تأیید ادمین

وضعیت فعلی فرانت: **۲۷ صفحه کامل پیاده‌سازی شده** و با دادهٔ seed محلی کار می‌کند.
همهٔ محاسبه‌های مالی در لایهٔ خالص `src/domain/` است و تست دارد.
کار بک‌اند: **جای‌گذاری منبع داده**، نه بازنویسی منطق.

## ۲. مهم‌ترین الزام معماری: Offline-First

این بخش را **قبل از هر چیز دیگری** بخوانید. تمام طراحی API به آن وابسته است.

### ۲.۱ قاعدهٔ اصلی

| کار | نیاز به اینترنت |
|---|---|
| **ورود (ارسال و تأیید OTP)** | ✅ بله — تنها جایی که اینترنت اجباری است |
| ثبت / ویرایش / حذف تراکنش | ❌ خیر |
| دیدن داشبورد، گزارش، مقایسه | ❌ خیر |
| بودجه، هدف، دسته، حساب | ❌ خیر |
| بینش و هشدار | ❌ خیر (محلی تولید می‌شوند) |
| خروجی CSV | ❌ خیر |
| خرید پلن و دیدن وضعیت پرداخت | ✅ بله (اما نبودش خطا نمی‌دهد، فقط «بعداً تلاش کن») |
| همگام‌سازی چنددستگاهی | ✅ بله (در پس‌زمینه، بی‌صدا) |

بعد از یک ورود موفق، اپ **باید تا ابد بدون اینترنت قابل استفاده باشد**.

### ۲.۲ ممنوعیت خطای شبکه

> **هیچ‌وقت، در هیچ صفحه‌ای، به‌خاطر قطع اینترنت خطا به کاربر نشان داده نمی‌شود.**

* نه Toast «اتصال برقرار نیست»
* نه صفحهٔ خالیِ «خطا در دریافت اطلاعات»
* نه Spinner بی‌پایان
* نه مسدود شدن دکمهٔ ثبت

رفتار درست: عمل کاربر **محلی انجام می‌شود، فوراً و موفق**، و در صف همگام‌سازی
می‌نشیند. تنها نشانهٔ حالت آفلاین یک **نشانگر بی‌صدا** است (مثلاً «همگام‌سازی
در انتظار») که خودش خطا نیست.

پیامد برای بک‌اند:

1. هیچ endpointی نباید در مسیر حیاتی (critical path) رندر یک صفحه باشد.
2. همهٔ نوشتن‌ها باید **idempotent** باشند (بخش ۲.۴) چون کلاینت با شبکهٔ
   نامطمئن چند بار تلاش می‌کند.
3. سرور باید **کل وضعیت** را در یک snapshot قابل دریافت بدهد تا کلایـنت
   بتواند آفلاین کار کند.

### ۲.۳ منبع حقیقت (source of truth)

| نوع داده | منبع حقیقت | دلیل |
|---|---|---|
| تراکنش، حساب، دسته، بودجه، هدف | **کلاینت**، سرور آینه و پشتیبان | کاربر باید آفلاین بنویسد |
| جلسه و توکن | **سرور** | امنیت |
| پلن، قیمت، سقف، ماتریس قابلیت | **سرور** | §۱ سند پلن‌ها — هیچ قیمتی در کد اپ hard-code نیست |
| entitlement (پلن فعال کاربر) | **سرور** | جلوگیری از دست‌کاری کلاینت |
| ساعت مرجع برای انقضای اشتراک | **سرور** (`server_time` در هر پاسخ) | با عوض کردن تاریخ گوشی نباید دوره کِش بیاید |

نکتهٔ مهم: entitlement از سرور می‌آید ولی **کش می‌شود**. اگر کاربر آفلاین بود،
آخرین entitlement کش‌شده معتبر است تا `expires_at` + یک **مهلت لطف ۷ روزه**
(grace period). بعد از آن اپ به پلن رایگان برمی‌گردد — نه به صفحهٔ خطا.

### ۲.۴ همگام‌سازی

مدل: **صف تغییرات محلی + pull تغییرات سرور**.

هر تغییر محلی یک رکورد در صف می‌شود:

```json
{
  "op_id": "uuid-v4 تولید کلاینت",
  "entity": "transaction | account | category | budget | goal",
  "action": "create | update | delete",
  "payload": { },
  "client_updated_at": 1735000000000
}
```

قواعد:

* `op_id` **یکتا و تولیدشدهٔ کلاینت** است. سرور اگر `op_id` تکراری دید، عمل
  را دوباره اجرا نمی‌کند و همان نتیجهٔ قبلی را برمی‌گرداند (idempotency).
* شناسهٔ موجودیت‌ها هم **کلاینت** می‌سازد (UUID). سرور ID نمی‌سازد، چون کاربر
  آفلاین تراکنش ساخته و آن ID الان در صفحهٔ او هست.
* حل تعارض: **last-write-wins بر مبنای `client_updated_at`**، به‌جز حذف
  که همیشه برنده است (tombstone).
* حذف نرم (soft delete) با `deleted_at` تا دستگاه دیگر هم خبردار شود.
* `sync_cursor`: سرور در هر پاسخ sync یک cursor می‌دهد؛ کلاینت بار بعد آن را
  می‌فرستد و فقط دلتا می‌گیرد.

جزئیات در `API-SPEC.md` §۵.

## ۳. جریان کاربر (User Flows)

### ۳.۱ ترتیب راه‌اندازی

```
نصب → ورود با OTP → آنبوردینگ (۴ صفحه) → اپ
```

کاربرِ برگشته هیچ‌کدام از دو مرحلهٔ اول را دوباره نمی‌بیند.
آنبوردینگ فقط یک‌بار (پرچم `onboardingSeen` محلی).

### ۳.۲ ورود

1. کاربر شماره موبایل می‌زند (هر فرمتی: `+98`، `0098`، ارقام فارسی، فاصله و خط تیره).
   کلاینت نرمال می‌کند به `09xxxxxxxxx` و فقط پیش‌شمارهٔ موبایل ایران می‌پذیرد
   (`^09[0-3|9]\d{8}$`) — خط ثابت رد می‌شود چون پیامک به آن نمی‌رسد.
2. `POST /auth/otp/request`
3. کد ۶ رقمی، اعتبار ۱۲۰ ثانیه، اجازهٔ ارسال دوباره بعد از ۶۰ ثانیه.
4. `POST /auth/otp/verify` → access token (کوتاه‌عمر) + refresh token (چرخشی)
5. سقف ۵ تلاش، بعد قفل ۱۵ دقیقه‌ای.

> ⚠ **الزام امنیتی**: پیام خطا هرگز نباید بگوید شماره ثبت شده بود یا نه
> (enumeration resistance). پاسخ `otp/request` برای شمارهٔ موجود و جدید
> **یکسان** است. تنها چیزی که در خطای verify گفته می‌شود: «کد درست نبود».

> ⚠ مقایسهٔ کد باید **زمان‌ثابت** باشد. محدودیت نرخ روی شماره **و** IP.
> اعداد بالا (طول، TTL، سقف) در کلاینت فقط برای UX است؛ **اعتبارسنجی واقعی
> کار سرور است** و کلاینت هیچ‌وقت مرجع نیست.

> ⚠ توکن‌ها در **Keychain/Keystore** می‌نشینند، نه AsyncStorage.
> AsyncStorage روی اندروید رمزنگاری‌نشده است.

### ۳.۳ مدیریت دستگاه‌ها

کاربر باید فهرست جلسه‌های فعال را ببیند و هر کدام را قطع کند («خروج از دستگاه
گم‌شده» برای یک اپ مالی الزام است، نه تجمل).
هر جلسه: نام دستگاه، آخرین فعالیت، شهر تقریبی، و پرچم «همین دستگاه».

### ۳.۴ خروج

خروج **دادهٔ محلی را پاک نمی‌کند** و همین باید به کاربر گفته شود.
پاک کردن داده یک عمل جداگانه است (`wipeAll`).

### ۳.۵ خرید پلن (کارت‌به‌کارت)

```
صفحهٔ پلن‌ها → انتخاب پلن و مدت → ساخت درخواست پرداخت (کد پیگیری ۶ کاراکتری)
→ کاربر کارت‌به‌کارت واریز می‌کند → رسید را می‌فرستد
→ ادمین در پنل تأیید/رد می‌کند → entitlement به‌روز می‌شود
```

* کد پیگیری عمداً **بدون `0/O` و `1/I/L`** است (الفبا: `23456789ABCDEFGHJKMNPQRSTUVWXYZ`)
  چون کاربر باید آن را از روی صفحه بخواند و تایپ کند.
* درخواست `pending` تکراری برای **همان پلن و همان مدت** دوباره ساخته نمی‌شود؛
  همان قبلی برمی‌گردد. دو کد پیگیری برای یک واریز یعنی ادمین نمی‌داند کدام را
  تأیید کند.
* مهلت درخواست: **۷۲ ساعت**.
* شماره کارت، نام صاحب حساب و شمارهٔ تماس رسید **از کانفیگ سرور** می‌آیند،
  هرگز در کد اپ ثابت نمی‌شوند.

## ۴. مدل داده

تایپ‌های دقیق در [`src/types/models.ts`](../src/types/models.ts). خلاصه:

### ۴.۱ Transaction

دو شکل دارد و این تمایز در تایپ اجبار شده:

```ts
// درآمد / هزینه
{ id, type: 'expense' | 'income', amount, name, note?, category, account }

// انتقال — category و account ندارد
{ id, type: 'transfer', amount, name, note?, from, to }
```

> **BR-01**: انتقال نه درآمد است نه هزینه. در **هیچ جمعی** شمرده نمی‌شود و
> هرگز سبز یا قرمز نیست. سرور هم باید همین را در هر aggregate رعایت کند.

### ۴.۲ Account

```ts
{ id, name, icon, balance, card: { bin, last4, expiry, bank, tone } | null }
```

> ⚠ **فقط چهار رقم آخر کارت** ذخیره می‌شود. PAN کامل هیچ‌جا — نه در اپ، نه در
> دیتابیس، نه در لاگ — ذخیره یا نمایش داده نمی‌شود.
> حساب «نقد» کارت ندارد (`card: null`)؛ دادن شمارهٔ کارت به پول نقد اطلاعات غلط است.

### ۴.۳ Category

```ts
{ id, name, icon, color, custom?: boolean }
```

دستهٔ پایه حذف نمی‌شود؛ دستهٔ ساختهٔ کاربر (`custom: true`) حذف می‌شود اما فقط
اگر تراکنشی به آن وصل نباشد. ترتیب دسته‌ها قابل جابه‌جایی است و باید ذخیره شود.

### ۴.۴ Day

تراکنش‌ها گروه‌بندی‌شده در روز:

```ts
{ id, iso, relative: string | null, label: string, items: Transaction[] }
```

* `iso` تاریخ میلادی، فقط برای محاسبهٔ دوره.
* `label` برچسب جلالی که به کاربر نشان داده می‌شود.
* سرور باید تراکنش را با **تاریخ ISO** ذخیره کند؛ گروه‌بندی روزانه و برچسب
  جلالی کار کلاینت است.

### ۴.۵ Budget / Goal

```ts
Budget: { id, category, limit, spent }
Goal:   { id, name, target, current, monthlyNeed: number|null,
          monthsLeft, deadline, status: 'ontrack'|'behind'|'complete' }
```

`spent`، `monthlyNeed` و `status` **مشتق‌اند** و ذخیره نمی‌شوند (BR-02).

### ۴.۶ Alert / Insight

```ts
Alert:   { id, kind, severity: 'info'|'attention'|'important',
           mark, title, sub, target, date, read }
Insight: { id, rule, severity, mark, title, sub, date, detail,
           figures: [{label, amount}], txIds: string[],
           action: { label, to } | null }
```

هفت نوع هشدار (FR-ALR-01…07): `budgetNear`, `budgetOver`, `spendingSpike`,
`recurringDue`, `balanceDrop`, `goalBehind`, `savingRateDown`.

**تولید بینش و هشدار محلی است** تا آفلاین کار کند. سرور فقط برای
push notification و برای همگام کردن پرچم `read` لازم است.

### ۴.۷ Summary

```ts
{ totalBalance, period, expense, income, saving, savingRate,
  txCount, topCategory, changeVsLastMonth, daysLeftInMonth }
```

> **BR-02 / P6**: هیچ‌کدام از این اعداد ذخیره نمی‌شوند. همه از روی خود
> تراکنش‌ها و حساب‌ها مشتق می‌شوند. اگر سرور جایی این را کش کرد، کش باید
> قابل بازتولید و بی‌اعتبارشدنی باشد.

### ۵.۵ قاعدهٔ صف‌شدن اشتراک

وقتی ادمین پرداخت را تأیید می‌کند:

* پلن **بالاتر** از پلن فعال → **فوراً** شروع می‌شود.
* پلن **هم‌سطح یا پایین‌تر** و دورهٔ فعلی هنوز فعال → **پشت** دورهٔ فعلی صف
  می‌شود (روز پولی هدر نمی‌رود).

صفحهٔ وضعیت باید فرق «الان فعال شد» و «بعد از پایان دورهٔ فعلی شروع می‌شود» را
بگوید؛ قاطی کردنشان یعنی دروغ. پس روی خود درخواست `queued`, `starts_at`,
`ends_at` ثبت می‌شود.

### ۵.۶ دورهٔ آزمایشی

۳۰ روز پرو، یک‌بار برای هر شماره (`trial_used`). تشخیص سوءاستفاده کار سرور است.

## ۶. تنظیمات کاربر

فهرست کامل در [`src/store/useSettingsStore.ts`](../src/store/useSettingsStore.ts).

تنظیمات **محلی‌اند** و برای کار اپ به سرور نیاز ندارند؛ اما برای همگام‌سازی
چنددستگاهی باید در سرور هم آینه شوند (به‌جز موارد امنیتی).

| گروه | کلیدها |
|---|---|
| ترجیحات | `calendar` (jalali/gregorian)، `digits` (fa/latin)، `weekStart` (sat/mon)، `reportChart` (bars/donut)، `reportStory`، `homeSections` |
| امنیت | `appLock`، `biometric`، `autoLock` (ثانیه) |
| حریم خصوصی | `benchmarking` (پیش‌فرض **خاموش**، عمداً)، `localOnly` |
| اعلان‌ها | ۷ کلید هشدار + `quietHours`، `quietFrom`، `quietTo` |

> ⚠ `appLock` و `biometric` در کلاینت فقط یک **سوییچ** هستند. رمز، کلید و توکن
> هیچ‌وقت در AsyncStorage نمی‌نشیند؛ پیاده‌سازی واقعی با Keychain/Keystore است.

> ⚠ `localOnly` = «داده‌ام از گوشی بیرون نرود». اگر روشن بود، **همگام‌سازی
> کامل غیرفعال می‌شود** و فقط auth و billing با سرور حرف می‌زنند. سرور باید
> این را محترم بدارد.

> ⚠ `benchmarking` (مقایسه با میانگین کاربران) پیش‌فرض خاموش است و داده‌اش باید

## ۷. قواعدی که سرور هم باید رعایت کند

هر جا سرور aggregate می‌سازد یا داده اعتبارسنجی می‌کند، این‌ها باید برقرار باشند:

| کد | قاعده |
|---|---|
| **BR-01** | انتقال در هیچ جمعی شمرده نمی‌شود |
| **BR-02 / P6** | موجودی و جمع‌ها محاسبه می‌شوند، ذخیره نمی‌شوند؛ هر عدد باید تا خود تراکنش دنبال‌شدنی باشد |
| **NFR-10 / §18.7** | نه PAN کامل، نه رمز، نه توکن در جایی که رمزنگاری‌نشده است |
| **§۱ بند ۴** | زمان مرجع اشتراک = ساعت سرور، در هر پاسخ `server_time` بیاید |
| **§۷.۱** | درخواست pending تکراری ساخته نمی‌شود |
| **§۶.۲** | قاعدهٔ صف‌شدن پلن (بخش ۵.۵) |
| **§۹.۳** | بودجهٔ رد شده از سقف، سرریز را نشان می‌دهد، نه نوار پرِ ۱۰۰٪ |
| **enumeration** | پاسخ OTP برای شمارهٔ موجود و جدید یکسان |

## ۸. نکته‌های غیرفنی مهم

* **همه‌چیز فارسی و RTL** است. پیام‌های خطای سرور که به کاربر نشان داده می‌شوند
  باید فارسی و انسانی باشند، نه `ValidationError: field required`.
  ساختار خطا در `API-SPEC.md` §۲.۴.
* **ارقام**: سرور همیشه عدد لاتین و `number` می‌فرستد. تبدیل به ارقام فارسی
  کار کلاینت است.
* **تاریخ**: سرور همیشه **ISO 8601 با timezone** می‌فرستد (`2026-09-25T10:00:00Z`)
  یا epoch milliseconds. تبدیل جلالی کار کلاینت است. **هیچ تاریخ جلالیِ
  رشته‌ای در API رد و بدل نمی‌شود.**
* **پول**: همیشه **تومان، عدد صحیح**. هیچ اعشاری، هیچ ریالی، هیچ رشته‌ای.

## ۹. اولویت پیاده‌سازی

| فاز | محتوا | چرا |
|---|---|---|
| **۱** | Auth (OTP، refresh، جلسه‌ها) | تنها چیزی که اپ بدونش بالا نمی‌آید |
| **۲** | Billing (پلن‌ها، entitlements، درخواست پرداخت، پنل ادمین) | درآمد |
| **۳** | Sync (snapshot + delta + صف idempotent) | پشتیبان‌گیری و چنددستگاهی |
| **۴** | Push notification برای هشدارها | افزوده |
| **۵** | قابلیت‌های `soon` (AI، OCR، خانوادگی، …) | V2/V3 |

فاز ۱ و ۲ کافی است تا اپ به‌صورت تجاری منتشر شود؛ فاز ۳ اپ را از «تک‌دستگاهی
با ریسک از دست رفتن داده» به «قابل اعتماد» می‌برد.
